# 共振法阵 / Sigilweave · 打磨路线与三人分工设计（TGA 2027）

> 版本 v1.2 ｜ 2026-11-16 ｜ 作者：年糕 + DSH
> 状态：**已过 builder check，待年糕确认后进入 writing-plans**
> 本文件只讲「未来十个月做什么、谁做、怎么验收」，不替代实现计划。
> v1.2 变更：**三人均写代码**，分工从「两码一内容」改为「三块互不重叠的代码所有权」。

## 一、意图与为什么

**为什么是现在**：项目已有五幕七场、1363 项测试全绿、网页版与 exe 都能跑。技术底座已远超任何学生赛的参赛门槛，真正的缺口不在「做得出」，而在「别人玩得懂、评委会给分」。三个人从没一起协作过，若直接开新坑，等于把已有资产全部折旧。

**为什么是这个目标**：年糕选定「冲比赛」，并且只冲腾讯游戏创作大赛（TGA），不参中国大学生计算机设计大赛（4C）、不参 Global Game Jam。4C 有「2026.7.1 前不得校外展出或获奖」的原创性条款，而本项目已在 GitHub Pages 长期公开，资格存疑；TGA 无此限制。

**不针对特定赛道优化**（年糕：就这样，不管什么赛道）。打磨按自由创意赛道的四维评审口径通用推进——作品创意、内容主题、视觉效果、游戏完成度——报名时按 2027 届实际开放的赛道选最贴的一条。不为了「AI 游戏赛道」强行接模型，也不为了「小红花」硬改题材。

**成功是什么样**：2027 年 9 月 15 日前，提交一份能让评委在 15 分钟内理解玩法、感受到差异、并玩到完整一局的 Demo，配套宣传视频、PPT、截图与中英双语文案。

## 二、目标 / 非目标 / 反目标

### 目标

1. **可理解性**：从未接触过本项目的人，5 分钟内能自己说出「我在做什么、怎么变强」。
2. **前 15 分钟质量**：比赛只看前 15 分钟，把最好的体验压缩进开场。
3. **完成度信号**：有配乐、有引导、有结局、有多阶段 Boss、无卡死与明显掉帧。
4. **中英双语**：全部玩家可见文本双语，UI 排版容纳英文长度。
5. **人类验证**：有真实外部玩家试玩记录；渠道未定期间用可自动判定的代理指标兜底（见 5.12）。
6. **参赛物料齐全**：Demo 包体 + 宣传视频 + PPT + 5 张以上宣传图 + 双语文案。

### 非目标（本周期明确不做）

- 不做联机、排行榜、账号系统、付费、内置广告。
- **不上架收费平台**（TGA 要求参赛作品 2026-01-01 前未商业化；免费网页版与免费 itch 页安全，Steam 售价会踩线）。
- **不做移动端适配**：只保 PC。现有手机适配已到「能操作」，本轮不再投入竖屏引导、触屏问答排版与手机 FPS 定档。标题页与报名页写明「建议 PC 浏览器」。
- 不新增第六幕或新角色（内容量已够，边际收益最低）。
- 不做 4C，不做 GGJ。
- 不做引擎迁移，不做 TypeScript 重写。
- 不针对 AI 游戏赛道接生成式模型（与零依赖离线交付冲突）。

### 反目标（即使技术上都成立，也算失败）

- 加了一堆功能但新手仍然看不懂 —— 等于没做。
- 为了「像商业游戏」而砍掉问答这个最独特的设计 —— 丢失差异化。
- 十个月后仍在改玩法，导致 9 月拿不出可提交版本。
- 双语只做了菜单没做内容，英文评委看到半截中文 —— 比纯中文更糟。
- 三个人同时改同一批文件，merge 冲突比功能开发还耗时 —— 等于白加一个人。

## 五、已定的决策（含理由）

1. **玩家可见文本外置为 `content/**.json`**，结构 `{ zh, en }`。理由有两条：一是双语必须靠内容层分离才能不散落在代码里；二是文本与代码解耦后，改文案不用碰逻辑、不用重跑全部断言。三人都会写代码这件事不取消这条——双语本身就要求它。
2. **前 15 分钟单独当成一条产品线重构**，不与全流程优化混在一起。评审只看开场，而现在开场是「走路找事件点」，是最弱的一段。
3. **问答系统保留并强化为叙事载体**，不改成一键跳过。这是本项目与所有同类割草构筑游戏最大的差异点；但必须让「不想答题就硬打过去」这条路在 UI 上同样明显（逻辑已支持，缺表达）。
4. **不追商业级美术**。程序化像素风格已自洽，重美术投入产出比最低；预算集中在配乐、UI 可读性、动效反馈。
5. **配乐用 WebAudio 程序化合成**，与现有 `src/audio/CineMusic.js`（89 行，正弦 detune 铺底 + cue 乐音）同一纪律，不引入外部音频资产与版权风险。
6. **不新增美术外包与外部依赖**，维持「单文件离线可玩 + 免费网页」的交付形态。
7. **中英双语**（年糕选定）。内容层从第一天就是 `{ zh, en }`，不是后期翻译。全球赛事评委可能看不懂中文；若 M0 之后再定，题库外置得整体返工。代价：UI 排版要为英文长度（约中文 1.5~2 倍）预留余量，480×270 面板会溢出。
8. **网页为主，exe 做离线兜底**（年糕选定）。性能以浏览器/集显为准；exe 只需断网能启动，不按 Electron 额外调优。网页端必须补「打开即玩」：现在开场 36 秒过场（`src/data/story.js` 六镜）+ 标题，评委不点跳过就白烧；M1 起默认可跳过，首屏给「立即开始」。
9. **只保 PC，不做移动端**（年糕选定）。移动端写进非目标，标题页与报名页写明建议 PC。
10. **中英文名分开**（年糕选定）：中文名 **共振法阵**，英文名 **Sigilweave**。游戏内中文文案用前者，英文文案与 GitHub 仓库、报名表英文栏用后者。不做全局改名，避免动 `index.html`、README 与测试断言。
11. **三人均写代码 → 按文件所有权切成三块**（年糕选定后我的方案，见第六节）。切法原则：每块内部高内聚、块之间只通过明确接口通信；共同修改的文件一律归一人独占；块大小尽量均衡（见第六节的行数估算）。
12. **试玩渠道未定，出口条件按可自动判定的代理指标写**（年糕：「人还在找，先按能拉到写」）。每个里程碑的强制出口是：**引导四步完成率埋点 + 5 人小样本记录 + 自动化冒烟**；外部人数作为加分项而非阻塞项。把不可控的外部资源写成硬出口，最终只会逼出假报告。
13. **内容外置范围 = 全部玩家可见文本**（我的判断）。不只 `encounters.js`，还包括 `src/data/story.js`（开场六镜、幕间、结局含名单）、`src/data/cinematics.js`（场次卡）、`src/ui/EncounterPanel.js`（面板固定文案，横竖各一套）、`src/scenes/TitleScene.js`（玩法说明整页）、`src/data/roster.js` 与 `card-hints.js`（卡牌描述）。只外置遭遇的话，到 M4 补叙事文本时才发现文本还在代码里，得返工第二次。
14. **`BattleScene.js` 归 A 独占，B 通过 hook 挂接**（我的判断）。A 在 M0/M1 交界先交一个约 4~8 人时的接口任务：事件总线 / `src/tutorial` 挂接点，让 B 的引导、配乐切换、问答入口表达都不必直改 2071 行的 `BattleScene.js`。直改会让它成为长期冲突热点，B 的三个任务都可能被打断；hook 换真并行，且 tutorial 能在不加载 Phaser 的纯逻辑环境里测。
15. **数值分成「全局系数」与「单体数值」两层**（我的判断）。全局倍率/曲线放 `src/logic/constants.js`（A 独占），单体敌人与 Boss 的数值放 `src/data/roster.js`（C 独占）。A 调平衡时只动全局系数，C 调配单体。这样平衡迭代不用两人抢同一个文件。若确实需要跨层调整，走每周同步，不直接改对方文件。
16. **平衡验收用可测量的代理指标，不承诺通关率**（我的判断）。`scripts/density-sim.mjs` 自己写明不含宝箱/幕间/Boss/问答，`balance-acceptance.mjs` 只量冷却受阻率，仿真天然测不出通关率。M3 平衡验收定为：仿真指标不回退 + 试玩 Top3 卡点关闭 + 「首局 15 分钟内死亡率」与「五幕通关率」作为观察值记录，不设硬门槛。设一个测不出来的门槛，最后只会拿假数据结项。
17. **小 Boss 差异化只做差异参数与弹幕，不重写行为系统**（我的判断）。从 20 只小 Boss 里挑 8 只，复用 `roster.js` 现有 elite 行为模板做参数/弹幕差异化，必要时新增 2~3 种行为。这是 C 的活。

### 为什么这样切

- **三条线各自能独立验证**：A 的逻辑有 Vitest，B 的 UI 有截图对比，C 的敌人与 Boss 有行为测试 + 内容校验脚本。
- **每块的出口对应明确里程碑**：A→M0 基线 / M1 平衡一 / M3 平衡二；B→M1 引导 / M2 配乐与开场；C→M2 Boss 表达 / M3 Boss 深度 / M4 双语内容。
- **冲突面最小**：唯一的高频共享点是 `BattleScene.js`，用决策 14 的 hook 隔开；数值用决策 15 的两层隔开。
- **试玩与物料不占代码时间**：C 的这两项是组织性工作，可与其他人的代码任务并行，不阻塞 main。

### 共享协作纪律

- **每周一次 30 分钟同步**：上周产出、本周计划、阻塞项、接口变更。
- **每周五出一个可玩版本**（main + Pages 自动部署），任何人都能点开链接验证。
- **main 永远可玩**：谁的改动让测试变红，谁当天修，不回滚别人的东西。
- **接口变更要先说**：跨块调用（A 的 hook、C 的数据结构、B 的 UI 事件）改形状前在同步里过一遍，不悄悄改。
- **内容校验进 CI**：`content/**.json` 由 `scripts/verify-content.mjs` 检查（字段完整、`zh`/`en` 双全、无重复 id、长度上限、不泄漏答案），不合规即构建失败。
- **分工不是永久契约**：M0 结束（约 8 周后）按实测工时重新分配一次，把最重的那块分一部分给最轻的那块。

## 十、本文档做出的自主判断（请年糕重点复核）

1. **三块分工的具体切法**（决策 11 + 第六节）：A 战斗核心+集成、B 表现层+引导+音频、C 敌人与 Boss+内容+物料。若 B/C 的技术方向和你设想的不同（比如 C 更擅长前端、B 更擅长逻辑），这条要调。
2. 内容外置做**全量可见文本**（决策 13），M0 因此变大。
3. **`BattleScene.js` 用 hook 不直改**（决策 14），M0/M1 交界多一个 4~8 人时接口任务。
4. **数值分两层**（决策 15）：全局系数 A、单体数值 C。
5. 平衡验收**不承诺通关率**（决策 16）。
6. 小 Boss 差异化**不重写行为系统**（决策 17）。
7. 「不管什么赛道」被理解为**按自由创意赛道四维通用打磨**，不做任何赛道特化。
8. **分工不是永久契约**：M0 结束按实测工时重分一次。
